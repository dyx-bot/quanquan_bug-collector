# quality-checklist.md — 运行质量自检与交付验收清单

> 版本：V0.1.5（2026-11-26，首轮离线测试 FAIL 后 P0 整改：新增 QC-40~QC-45 确定性身份/时间/归属/留痕/统计与校验闸门，校验闸门 FAIL 时相关项不得 PASS）。
> V0.1.4 变更：QC-26/27/34/35 同步分环境状态、事件去重唯一口径与配置合并/生效配置。
> 引用入口：`SKILL.md` §6「交付前检查」、§7「配套文件与加载约定」。
> 加载时机：`offline / collect / process / analyze` 每次运行交付前；正式写入前先检查本轮拟提交的数据与状态，写入后再核验实际结果。
> 职责：检查本轮是否遵守采集、筛选、去重、复发和输出规则，发现问题后纠正、降级或保留复核项。**不另行定义缺陷判据、业务枚举、统计公式或正式数据结构；不是独立 Skill 测试集，也不证明提取结果绝对正确。**

## 1. 执行方式

1. 以本轮实际加载的 Skill 版本、配置、输入快照及用户授权范围为检查基线。业务判定引用对应规则文件，字段、枚举、编号及引用路径以 `references/output-schema.md` 为准。
2. 按执行模式选择适用检查项，先检查数据完整性与权限，再检查处理过程和结果；不要求单次运行完成所有模式。
3. **确定性检查必须实际执行（V0.1.5 强制）**：先运行 `scripts/bc_preprocess.py`，再运行 `scripts/bc_validate.py`，把原始输入与实际输出逐条比对；不能以智能体口头声明、只查输出内部引用或「看起来对」替代。脚本 FAIL 的项，对应 QC 不得标 PASS。语义检查仍需回读原始证据。
4. 对每个适用检查项记录结论、检查范围和依据。自检结论使用以下四种标签（仅供自检报告，不属于案例库正式枚举）：

| 结论 | 含义 |
|---|---|
| PASS | 已执行检查，有证据支撑符合要求 |
| FAIL | 已发现明确违反规则或数据不一致 |
| PENDING | 证据不足、检查未完成或业务结论待人工确认，不能确认通过 |
| N/A | 不属于本轮模式或明确授权范围，须说明原因 |

5. 发现问题时优先修正本轮受影响产物并复查；无法修正时按 §8 处理，不伪造数据、人工结论或检查结果。预算不足时在安全批次边界停止，记录未检查项，不将 PENDING 当 PASS。
6. 同一次运行不得擅自改写规则、参考答案或项目配置来使自检通过。外部正式测试集的 `expected`、`assertions` 等参考答案不得用于被测 Skill 的执行或自检。

| §7 输出、编号与运行边界 | 必查 | 必查 | 必查 | 必查 |

离线分析不要求重新请求真实数据源、独立拉取未提供的 MR 或推进水位；只核对所给输入的覆盖范围。若离线输入缺少历史基线、完整正文、MR 快照、附件等，只能在实际证据范围内判断。缺证不是检查通过，也不代表缺陷不存在。本清单对所有模式都是交付前依据。核心七份文件为 SKILL + collection / filtering / dedup / recurrence / output-schema / quality-checklist；`offline`、`process`、`analyze` 必须全部加载，`collect` 至少加载 SKILL + collection + output-schema（recurrence 用于识别线索）；`process / analyze / collect` 另必读 `references/execution-rules.md`（offline 不读写水位与持久化、无该文件不适用）。不涉及的部分只在检查结论里标 `N/A` 并说明原因，但清单本身不能跳过。

## 3. 原始采集与完整性检查

依据：`references/collection-rules.md` §1–§6；`references/output-schema.md` §1.1、§4、§6、§10。

| ID | 检查项 | 检查方法与通过条件 |
|---|---|---|
| QC-05 | 原始证据保留 | 原始数据已保存（offline 为隔离输入或可回查副本）；关键正文未被筛选结果覆盖或截断；记录可定位到原文件及稳定身份。 |
| QC-06 | 范围及分页完整性 | 对照 manifest、实际文件条数、分页返回和查询范围；未完成分页、限量截断、超时、权限不足、未解释空结果均如实标注，不称全量。offline 仅验证提供的文件，不从样本推断全库覆盖。 |
| QC-07 | 来源身份及快照 | 同一来源稳定键正确，MR 键不含 state，其他键也不含可变属性；更新保留快照时间，旧状态不覆盖更新状态；同仓同 SHA 多 ref 扫描按记录去重，跨仓同 SHA 保留独立身份。 |
| QC-08 | 钉钉消息 | 群、完整 messageId、发送时间及发送人分别核对，发送人不是 messageId，时间字段不混入姓名；文本、引用/回复、前后文及附件引用可回查；缺失附件不补造；零关键词命中不等于没有问题。 |
| QC-09 | 禅道记录 | 确认产品与实例范围，不将个人视图当全量；标题、steps、状态、操作历史及更新时间等已按规则保留或注明缺失；明确不存在、无权限、查询异常分别记录，未确认编号留在缺口中。 |
| QC-10 | GitLab Commit | 同时保留 title、完整 message、SHA、项目身份及可获取的父提交和引用信息；不可达记录未被提前删除；父提交缺失时不伪造数量。 |
| QC-11 | GitLab MR 与对账 | 在线采集按范围独立获取 MR，并记录 Commit/MR 对账及未匹配项；orphan_mr 已评估或列入后续待处理批次。仅从 Commit/群消息提取的 MR 引用只作待核查线索（`mr_ref_unverified`），未写入 `kind=mr` 的证据快照，也未用作归并强证据。离线缺失 MR 输入时说明限制。 |
| QC-12 | 可达性与历史提交 | 对象存在、分支/标签可达性和内部引用分别记录；不把 refs 为空、SHA 可查询或查询失败直接等同于已确认悬空；具体历史重写原因必须有依据。 |

### 3.1 完整性判断注意事项

- `complete` 只用于实际声明的查询范围，须满足对应规则的分页、失败分类及缺口条件；有未确认缺口的批次不得标 `complete`。
- 区分原始记录数、去除重复采集后的记录数、证据记录数、候选数和缺陷数；不能要求不同口径的数字天然相等。
- 缺少材料时可以交付范围明确的部分结果，但必须说明哪些结论无法验证；不得为了补齐表格编造输入。

## 4. 数据清洗、规则筛选与缺陷提取检查

依据：`references/filtering-rules.md` §1–§7；`SKILL.md` §4.2、§4.3；`references/output-schema.md` §1.1、§3、§10。

| ID | 检查项 | 检查方法与通过条件 |
|---|---|---|
| QC-13 | 筛选覆盖与留痕 | 对照本轮已处理原始记录的 source_key 与 `filter_results.jsonl`，每条均有可追溯的分流结论、priority、triage_reason 和 reason；重复快照及决策历史可解释；`candidate_ids` 与 `candidates.jsonl` 的 `source_refs` 双向可回查（一条原始记录生成了哪些候选、候选来自哪条记录）。未处理记录明确挂起，不冒充完成。 |
| QC-14 | 排除与默认放行 | 排除项确属无关、模板或纯同步，有理由；未命中规则且不能确认无关的记录进入 candidate + low，未因格式异常、机器人身份或无关键词直接丢弃。 |
| QC-15 | Commit/MR 正文检查 | 普通与 Merge 提交均分析完整 message（`record_type` 已标注，`analyzed_fields` 含 `message_body`，截断时标 `message_body_truncated`），区分模板、引用与业务描述；按父提交数量 ≥2 识别 Merge；没有漏掉 feat 等其他前缀、无前缀、悬空提交或独立 MR 中的缺陷线索。 |
| QC-16 | 修复证据与独有候选 | 能对应已登记缺陷的修复记录按内容分配 role（`primary_fix` 主修 / `related_fix` 关联改动 / `status_evidence` 状态回执 / `background` 背景 / `report` 首报），未一律归为状态证据；无法对应但存在具体缺陷线索的记录产生 defect/suspect 候选；纯合并、部署或测试回执标 `sync`/`template` 留作上下文，不被误建为独立缺陷。 |
| QC-17 | 缺陷判定 | 回读上下文，确认 defect 有实际行为与预期不一致的依据；区分需求、优化、能力边界、执行/环境异常和疑似问题，不凭关键词、异常指标或缺少验证直接定性。证据不足进入复核。 |
| QC-18 | 提取粒度与事实 | 一条记录含多个独立问题时分别评估；多条描述同一问题时保留证据链；模块、触发、现象、预期、环境及根因均有依据，推断明确标注，未知项按 schema 留空或标未知并复核。 |
| QC-19 | 过程输出 | `candidates.jsonl` 可回溯到原始 source_refs；每个已完成候选有后续匹配或待处理记录；不存在无理由从筛选、提取到匹配阶段消失的记录。 |

重点回读：排除的 Merge/feat/无前缀记录、只有修复证据的候选、规则未命中记录、长消息多主题、需求与缺陷混合的消息。抽查须列出样本来源及数量；不能用抽查声称已验证全部语义判断。

## 5. 跨源关联、去重与证据归属检查

依据：`references/dedup-rules.md` §1–§7；`references/output-schema.md` §1.1、§3、§4、§7、§10。

| ID | 检查项 | 检查方法与通过条件 |
|---|---|---|
| QC-20 | 两层去重 | 记录层按稳定来源身份去重，实体层按缺陷同一性判定；不同源同内容不直接删除，同仓重复扫描不重复建号。 |
| QC-21 | 自动归并依据 | 逐项检查本轮自动归并，须满足 `references/dedup-rules.md` §2.1 的 high 全部条件（项目/模块一致、现象与触发一致或同根因、至少一条归属已核验的强证据、修复预期一致），并有「标识 + 内容」双核验依据；不能只凭同 MR/SHA/messageId/禅道号、标题相似、时间接近或未核实的 MR 引用归并。 |
| QC-22 | 问题链与待复核 | 需独立修复、独立验证的断点分别登记；同一问题的多次报告或多条修法不强制拆分；medium 转人工复核，low 不自动归并；不因时间窗截断跨期关联。 |
| QC-23 | 多对多证据与角色 | `role` 位于 `evidence.bug_links[]`，值符合 schema；一个 MR/Commit/消息可支撑多个缺陷，每个关联单独核验；不借用其他缺陷的合并、部署或复验回执。 |
| QC-24 | 来源状态与归并历史 | 同一缺陷的多个禅道单分别保存状态快照；保留被归并编号、指向及证据，不物理删除、不重置编号、不让发生历史被去重吞掉。 |
| QC-25 | 匹配与复核留痕 | `match_results.json` 中候选、目标及依据可回查，歧义记录有相似点、差异及缺失证据；人工 `resolution/resolved_by/resolved_at` 未由 AI 代填。 |

## 6. 生命周期、发生、复发与高频问题检查

依据：`references/recurrence-rules.md`、`references/output-schema.md` §3、§5、§7–§9；`SKILL.md` §4.5、§4.6。

| ID | 检查项 | 检查方法与通过条件 |
|---|---|---|
| QC-26 | 状态推进 | 源系统状态与本地 lifecycle 分开；MR 合并、禅道 resolved/closed、CI 通过不直接等于 verified_fixed；状态推进有本缺陷的证据及流转记录；`to=verified_fixed/closed` 的流转行按 §10.5 登记/核对其验证适用 `environment`（历史行缺失按证据原文核，不回填编造）。**`closed` 不新增/不扩大分环境验证范围；历史 `verified_fixed` 事实不因复发/回滚/关闭被抹去，撤销验证只能走有审计记录的反向流转（`references/recurrence-rules.md` §2.7，Q-03/Q-04）。** |
| QC-27 | 独立发生与持续处理 | 多人转述、重复截图、多轮补修不增加独立发生次数；`repeat_unresolved` 只在未解决期间出现新的独立触发/异常证据时存在，并计入 `independent_occurrences`、不计入复发；没有新证据时未按缺陷固定生成一条，持续未解决由 lifecycle/transitions 表达；证据不足只记录线索或复核。**按环境判定（§2.2，Q-05）：`first` 只登记主记录全局首次、不按环境重复；判定某环境未解决要查该环境 transitions 验证证据而非只看全局 lifecycle；同一缺陷在从未验证环境独立发生且证据充分登记 repeat_unresolved，不因缺部署记录否定该次发生，也不仅凭现象相似认定同一缺陷。** |
| QC-28 | 复发成立条件 | 每条已确认复发均有同一缺陷依据、此前**本次出现所涉环境（canonical_name）**修复验证通过的证据（验证范围判定见 `references/recurrence-rules.md` §2.6；同分类其他环境的验证不代偿），以及本次新的独立异常证据；仅重新激活进入 recurrence_signals/recurrence_check，不直接记复发（重新激活既非必要条件也非充分条件）；未仅凭「部署漂移/旧镜像」字样判定。 |
| QC-29 | 广义复发与子类型 | 回滚重现与 repeat_after_fix 均计入广义复发，保留子类型；逐项核对 `recurrence_events = repeat_after_fix 条数 + rollback_regress 条数`，子类型合计与总量一致；回滚子类型有版本/镜像/pin/配置恢复旧值等回退证据；修复从未生效与已部署未验证未被误计为复发。 |
| QC-30 | 同类风险与修复次数 | 独立同类缺陷登记 `first` 并建立 `similar_class` 关联，不新建 `related_case` occurrence，不增加彼此复发次数；fix_actions 为可选指标，可枚举独立处置时才计数，不用 MR、Commit 或消息数估算；未知填 null。 |
| QC-31 | 高频问题与测试候选 | 同类风险、反复未解决和复发不混为同一计数；测试候选可追溯到缺陷，包含有依据的场景、前置条件、预期与验证依据；缺失步骤/断言写 missing_info；不称已执行或已通过测试。 |

## 7. 数据结构、写入边界与输出检查

依据：`references/output-schema.md` §1–§10；`SKILL.md` §5、§6。

| ID | 检查项 | 检查方法与通过条件 |
|---|---|---|
| QC-32 | 文件与字段合法性 | 实际解析本轮 JSON/JSONL，核对必填字段、类型、枚举、时间格式及 null/unknown 规则；不得用示例值或空字符串冒充真实事实。 |
| QC-33 | 主键、引用与编号 | 各对象主键唯一；证据、发生、关联、归并和流转引用指向存在的对象，归并无环；正式编号稳定、不复用；离线使用 offline-<run_id>- 临时键。 |
| QC-34 | 输出统计一致性 | 从实际输出重算记录、缺陷（区分明确与疑似、归并别名）、发生（`independent_occurrences`，含 `repeat_unresolved`）、持续未解决（`repeat_unresolved_events`、`unresolved_open_bugs`）、复发（`recurrence_events` + 子类型）、`related_cases`、`bugs_without_occurrence` 及复核数量，并按事件去重（细则**以 `references/recurrence-rules.md` §3.8 为唯一权威**：主记录聚合先行；同一具体发生须有 `role=report` 现象报告类证据交集且反证阻断才合并；仅共享修复/部署/背景证据不算交集；歧义进复核并披露待复核数量）；与报告、过程文件一致；同时给出已确认数量、未知数量与 `coverage`（含时间精度覆盖）。`unresolved_open_bugs` 按 `bug_id` 计（不按环境计，全局 lifecycle 取最不先进环境状态）。`output-schema.md` §5/§10.4 只引用、不另立去重规则。不能核实的可选统计不强填，不能确定的业务总量明确范围或待复核。 |
| QC-35 | 运行概览与缺口披露 | 报告注明 run_id、模式、项目、版本、数据截止时间、批次、已完成范围、未覆盖部分及待复核项；历史已解决与新发现/待确认分开呈现。**运行开始先输出合并后的实际生效配置 `effective-config.json`，并核对项目配置按字段合并、默认固定约束（§2 第 6 条 / `config/default.json` `config_merge`）未被覆盖或放宽。** |
| QC-36 | offline 隔离 | 所有输出位于本轮隔离目录；未读取正式 state，未改动正式案例库、raw、水位及永久编号；未启动定时任务或写入真实业务系统。 |
| QC-37 | collect/process/analyze 权限 | 按 schema §1.3 校验实际写入范围；collect 不写 library 和正式编号；process 不推进未经验证的采集水位；analyze 只写 `reports/` 与运行日志，需要改 lifecycle / 新增 occurrence / 分配编号时输出「待 process 处理」清单而非直接改库；人工结论字段不代填。 |
| QC-38 | 水位、持久化与重跑 | 正式运行对照旧/新状态、manifest 和实际存储；未确认缺口不被跨越，processed_through 不超过 collected_through；库、批次与编号状态一致提交，写后回读确认；MR 未实际合入并验证不报完成；冲突或验证失败不推进正式水位。分批、幂等重放与失败恢复的执行细则对照 `references/execution-rules.md` §2–§3、§6–§7 核验；正式模式下该文件缺失时相关检查不得标 PASS（转 PENDING，按 `SKILL.md` §7 降级）。 |
| QC-39 | 执行预算及续跑 | 遵守已确认运行限制（单条命令 ≤60 秒、单轮预算 3 分钟、无后台任务）；预留保存及验证时间；未完成批次标明续跑位置，不以生成报告替代实际处理。 |

| QC-45 | 校验闸门执行（V0.1.5） | 交付前已运行 `bc_validate.py` 并保存报告；`fail_count=0`；仅 WARN 时按 PENDING 说明，未把未跑/FAIL 写成 PASS；修复后重跑记录保留。 |

### 7.1 检查深度

- 全量结构检查（在本轮已处理的有限批次内）：JSON/JSONL 解析、主键唯一、引用完整、枚举、记录覆盖、计数、写入范围、水位条件。优先脚本一次完成。
- 重点语义复核：本轮自动归并、已确认复发、推进 verified_fixed/closed 的记录及存在证据冲突的记录逐项核对；对低优先级及排除项进行有记录的抽查。未能完成的关键核对不得标 PASS。
- 语义自检不替代独立测试，也不产生人工确认；不能仅靠检查字段存在就证明缺陷内容准确。

## 8. 问题处理、交付条件与自检报告

### 8.1 问题处理

| 情况 | 处理方式 |
|---|---|
| 原始证据被丢弃、身份或引用错误、越权写入、编号冲突、未核实持久化、缺口被水位跨越 | 阻止受影响正式写入或停止后续推进；保留现场、记录失败并核验修复。不得宣称成功。 |
| 误提、漏提、错并、错拆、证据归属或状态/复发定性错误 | 回读证据，纠正本轮输出及受影响统计；不具备纠正依据则降级为疑似/待复核，保留审计记录。 |
| 输入不完整、语义不确定或规则冲突 | 保留原始证据，标注 PENDING、影响范围及下一步核验材料；可交付不受影响部分。 |
| 展示或格式问题 | 修正后重新解析/核对；不可修正时注明影响，不隐瞒机器可读数据失效。 |

### 8.2 交付判断

- **通过自检**：所有适用必查项已执行，受影响的关键检查无 FAIL 或 PENDING；`bc_validate.py` 无 FAIL（仅有 WARN 时按 PENDING 说明）；N/A 有范围说明。仍不代表独立测试已通过。
- **部分完成**：存在输入缺口、规则冲突、待核验业务判断或未完成检查；明确哪些结果可用、哪些不可用及续跑位置。正式采集批次的 completeness 仍按采集规则判断，不由本节覆盖。
- **阻止正式提交/未确认提交**：存在影响数据完整性、权限、编号、水位或持久化的未解决错误；不得推进受影响状态或将拟写入内容称为正式入库结果。

两类 PENDING 必须分清，不得混为一谈：

- **业务待复核**：规则已正确执行、复核记录已按 schema 生成（如 `medium` 归并候选、`recurrence_check`、`field_verify`），只是结论要人工确认。这种情况下**对应的流程检查可以通过**，但业务结论仍标未确认；不等于整个任务失败。
- **自检未完成**：检查项没执行、证据没回读、批次被预算截断或工具失败。这种情况下**该检查项本身不得标 PASS**，任务只能算部分完成，须写明未检查范围与续跑位置。

### 8.3 最小自检报告（随运行日志或离线报告交付）

以下为报告模板，而非新增正式 schema。实际检查时填写，不得把模板本身当成执行结果；正式运行日志结构由 `references/output-schema.md`（`runs/<run_id>.json`）约定，分批与恢复细节的规则由 `references/execution-rules.md`（V0.1.3 起已编写）承载。


## 9. 与独立测试集的边界

- 本清单是每轮运行的通用自检规则，不保存任何具体测试案例的标准答案，也不要求智能体给自己评估测试准确率。
- Skill 开发阶段的离线评测只向被测智能体提供固定版本的 Skill 与独立测试输入；人工确认的 expected-results、断言及判分依据由独立评审环境使用。
- 需要对照断言时，以实际输出的过程记录、案例库及证据为准。不能从未输出的中间步骤推定其已正确执行；必要时标记无法判定，并在后续规则/输出一致性修订中补齐观测依据。
- 评测失败反馈到规则修订和回归测试，但不得为迎合实际输出而改动正确的参考答案。业务预期的变更需说明证据、原因并经确认后再固定版本。
