# dedup-rules.md — 跨源关联、去重与问题链拆分规则

> 版本：V0.1.4（2026-11-26，随版本同步：§4.3/§7 事件去重改为引用 recurrence-rules §3.8 唯一口径）。
> 引用入口：`SKILL.md` §4.4「跨源关联与去重」。
> 加载时机：`process` 模式（候选入库前）；`analyze` 模式复核归并关系时；`offline` 模式同样加载。
> 分工边界：独立发生与复发的判定见 `references/recurrence-rules.md`；数据结构与编号见 `references/output-schema.md`。本文件回答两个问题：**这些证据是不是同一条记录/同一个缺陷**；**什么时候该拆开而不是合并**。

## 1. 两层去重
1. **来源记录重复**（record-level）：同一来源身份下的同一条记录因重放、多分支扫描、转发被采到多次——用幂等键判重（`references/collection-rules.md` §6.1），合并快照即可，不产生语义工作。
   - 记录身份 = 来源 + 系统/实例/项目范围 + 稳定键。同一项目不同分支扫到同一 SHA 属记录重复；**不同仓库（项目 ID）的相同 SHA 不属于记录重复**，各自保留来源身份，可登记等价关系（§4.2）。
2. **缺陷实体重复**（entity-level）：不同来源的候选描述的是同一个需要独立处理的问题——本文其余部分针对这一层。

先做 1 再做 2。不要把「证据出现两次」当成「缺陷重复」，也不要把「两个来源都报了」直接当成两个缺陷。

## 2. 匹配次序（从硬到软）
| 层 | 信号 | 动作 | 可能结果 |
|---|---|---|---|
| L0 编号匹配 | 候选中出现禅道号 / bug 链接 / MR 引用，且与历史库已登记编号一致 | 核验编号归属后建档关联 | match / related（**编号只是线索，需核验归属**） |
| L1 证据链匹配 | 候选共享同一证据（同 messageId、同 SHA、同 MR、同一张附件或日志） | 建立证据关联 | 仍需判定缺陷同一性 |
| L2 语义比对 | 标题/模块/现象/触发条件/环境相似（环境按 canonical_name 判） | 按置信等级自动或转复核 | new / merge_into / related_to / review |
| L3 人工复核 | 证据冲突或模糊 | 进 review_queue | 人工结论 |

- 时间窗（默认 30 天，可配置）只用于缩小 L2 候选池与排序；**不得**因超出时间窗直接排除——跨期复发必须能穿透时间窗（兜底见 `references/recurrence-rules.md`）。
- 语义比对先按「项目 → 模块 → 环境」收窄，再比现象与根因描述；跨项目不自动归并。**环境按 canonical_name（`config/projects/<project>.json` environment_registry）收窄；同分类不同环境是两个环境，不视为同环境**（口径见 `references/recurrence-rules.md` §2.6、`references/output-schema.md` §10.5）。

### 2.1 语义去重置信等级
| 等级 | 条件（需同时满足） | 动作 |
|---|---|---|
| `high` | 项目/模块一致；现象与触发条件一致或可由同一根因解释；至少一条**强证据且归属已核验**（同禅道编号确认是该单的转述、同 MR 的 diff 覆盖该现象、同仓同 SHA、同一截图/日志内容一致）；修复预期一致 | 允许**自动归并**（merge_into），保留归并理由 |
| `medium` | 上述条件大部分满足，但存在一项差异（版本/环境不同、模块不明确、证据只有单条硬线索）或语义高度相似但硬证据未核验 | **不自动归并**，进 review_queue 待人工复核 |
| `low` | 仅共享编号 / SHA / MR / messageId / 相似标题 / 同一时段，缺少内容层面的吻合 | 不归并；登记 related_to（如确有关联）或 review |

- **共享标识不能单独作为归并依据**：同一个 MR 可能修多个缺陷，同一个 SHA 可能是镜像，同一个 messageId 可能只是转发，同一个禅道号可能被讨论另一现象。标识必须加上「归属核验 + 内容吻合」才升为强证据。
- **未核实的 MR 引用不是强证据**：commit message 或群里出现的 `!iid` 链接，若本批次没有独立采集该 MR 并核对归属，只能算待核查线索（`mr_ref_unverified`），不能作为 high 的「强证据」，也不能据此归并。
- 本节是 `high / medium / low` 的**唯一定义位置**；`SKILL.md`、`quality-checklist.md` 等只引用不另设标准，不得擅自放宽自动归并门槛。若实测发现门槛拖累自动化效率，只能记为后续优化建议，本轮不放宽。
- 置信等级是判定结果的一部分，写入 `match_results`；不得只记录「相似」而不记录依据。

## 3. 证据身份 ≠ 缺陷身份
- 一条群消息、一个 Commit、一张禅道单都是**证据**；一个缺陷是**需要独立处理与验证的问题**。
- 经核实的同一禅道编号是强线索：候选即该单的转述/截取 → match；候选只是引用该单讨论另一现象 → related。区分关系角色：**主修**（该 MR/单就是修它）、**关联**（同链路顺带改动）、**背景引用**（截图/日志里顺带出现）、**状态证据**（解决/部署/复测回执）、**报告**（现象首报或复述）。
- **role 定义在「缺陷 ⇄ 证据」的关联关系上，不是证据的固有属性**：同一证据对缺陷 A 可以是 `primary_fix`，对缺陷 B 可以只是 `background` 或 `status_evidence`；`role` 随关联写入 `evidence.bug_links`（见 `references/output-schema.md` §4），不能写在证据主体上。
- 同一 MR / SHA / messageId 出现在多个候选 ≠ 这些候选是同一缺陷：一个 MR 可以同时修多个缺陷，一个 commit 可以夹带无关改动；归属以 diff 与描述为准。
- `Merge branch` 类模板正文不算业务证据；归属判断看 diff 内容与 MR 描述。
- 正则按来源系统区分编号格式：禅道 `#123` 与 MR `!123` 不可混用。

## 4. 归并判据与反例

### 4.1 判同一缺陷（merge_into）需同时满足
1. 项目、模块一致（模块不明确时现象高度一致可代偿）；
2. 现象与触发条件一致，或可用同一根因解释；
3. **标识与内容双核验**：共享编号需确认归属；同 MR 需 diff 覆盖该现象；同 SHA 需同项目或已登记等价关系；同截图/日志需内容一致。单独共享标识不满足本条；
4. 修复预期一致（同一改动应能同时消除两处现象）；
5. 按 §2.1 判定置信等级为 `high` 才自动归并；`medium` 转人工复核，`low` 不归并。

### 4.2 不归并的反例（历史教训固化）
- 同一天两个群出现的相似现象，但模块/版本不同 → 先核对版本再定。
- 同一 MR 修复的两个独立缺陷 → 拆开，MR 作为共同证据。
- 同一时段、同一链路上的不同断点 → 拆开并关联（见 §5）。
- **不同仓库的相同 SHA（镜像仓库、fork）→ 不是记录重复，也不是同一缺陷的当然证据**：各自保留来源身份，登记 `equivalent_refs`（kind=mirror_repo / fork），只在内容与归属都吻合时才作为关联线索。
- 标题相似，但一个有复现、另一个无复现且环境不同 → review，不自动并。
- 禅道单被反复激活 → **不是多个缺陷，也不是已确认的多次发生**：重新激活只作为复发线索，须有新的现象/时间/环境证据核验后才登记 occurrence（见 `references/output-schema.md` §5、§8）。
- 仅共享禅道号、MR、SHA 或 messageId 且无内容吻合 → 不归并，按 §2.1 降为 `medium`/`low` 处理。

### 4.3 归并操作
- 主记录选择：已有禅道单者优先作为业务锚点（source_status 保留其快照）；内部主记录选证据最全的一条。一个缺陷可关联多个禅道单（§3、`references/output-schema.md` §3），不以单号为唯一锚点。
- 保留全部：原编号转入 `merge.merged_into` + `merge.reason` + `merged_at`，证据映射整体保留，不物理删除；允许 unmerge（同样留审计记录）。
- 归并不改变 occurrence 的归属——复发历史必须跟着原缺陷走。**统计按主记录聚合**：别名记录的 occurrence 通过 `merge.merged_into` 归入主记录；是否同一事件**按 `references/recurrence-rules.md` §3.8 判定**（要求 `role=report` 现象报告类证据交集、排除仅共享修复证据、反证阻断，§3.8 为唯一权威定义），只计一次，主记录与别名不得各自重复计数。报告必须列出别名及其归属，审计信息（原编号、证据映射、发生记录）不因归并丢失。
- **归并时 occurrence 只迁移、不重判**：别名记录的发生记录移入主记录后，其 kind、observed_at、证据保持原样；如需按新证据重新判复发或事件去重，按 `references/recurrence-rules.md` §2、§3.8 用**主记录全量证据**单独判定，不得在归并动作内顺手改判或补计任何一方的复发次数。
- 多个候选都似同一缺陷但证据不确定时：不归并，全部挂 review。
- 自动归并必须记录 `confidence=high` 与判定依据；人工复核的归并记录 `resolved_by / resolved_at`。

## 5. 问题链拆分（历史经验固化）
一次故障报告往往是一条链，不是一条缺陷：
- **同一次故障**（同一时段、同一诱因、用户感知为「一件事」）内的多个技术断点——数据层（脏数据/配置错）、服务层（异常未兜住）、客户端层（展示错）、流程层（人工步骤遗漏）——按「是否需要**独立修复并独立验证**」决定拆分；需独立处理的登记为独立缺陷，并用 `related` 关联（kind=same_incident / caused_by / blocked_by）。
- 判定顺序：先看修复手段（一个改动能同时闭环的倾向合并）→ 再看验证手段（需分别验证的倾向拆开）→ 最后看归属模块。
- 避免拆分过度：报错文案不同、不同用户撞到同一问题、同一缺陷的多张截图，都不是拆分理由。
- 不得按「同一时段的消息或 MR」批量推断归属——归属逐条判定。
- 已修复后再次出现 → 不是拆分也不是重复：走复发登记（`references/recurrence-rules.md`）。

## 6. 输出与人工复核
- 每个候选输出 match_result：`new | merge_into | related_to | duplicate_record | review`，附 `confidence`（high/medium/low）与 match_basis（支持判定的证据/维度清单），写入 `process/<batch_id>/match_results.json`。
- 相似度维度建议（各记 0/1，汇总展示，不强制加权）：模块一致、现象一致、根因一致、环境一致（canonical_name 相同；同分类不同环境记 0）、时间窗内、证据共享（现象报告类）、标识归属已核验。
- 有歧义时进 review_queue，保留 `similar_points`、`differences`、`missing_evidence` 三项；**人工结论字段（resolution/resolved_by/resolved_at）不得由 AI 预填**。
- 跨源映射（缺陷 ↔ 禅道号 ↔ MR/SHA ↔ 群消息的多对多矩阵）是去重结果的对外呈现，结构见 `references/output-schema.md` §9 表 4。

## 7. 自检（对照 SKILL.md §6）
- 每个自动归并都说得出「标识 + 内容」双核验的硬证据且置信为 high；说不出退回 review。
- 没有仅凭共享编号/SHA/MR/messageId 就归并的情况；镜像仓库同 SHA 没有被误并；未核实的 MR 引用没有被当成强证据。
- 归并后统计按主记录聚合：别名记录的 occurrence 已归入主记录，同一事件（按 `references/recurrence-rules.md` §3.8 判定，非任意证据交集）没有被主记录与别名各计一次；别名、原编号与证据映射仍可查；归并动作本身没有重判发生/复发或补计次数（需要重判时按 `references/recurrence-rules.md` §3.8 用主记录全量证据单独判定）。
- 独立断点没有被错并；问题链每一段在设计上可独立验证。
- 复发记录没有被去重吞掉：「重复描述」与「再次发生」分别登记；重新激活没有被直接当成新发生。
- 证据身份与缺陷身份未互相覆盖：同编号的禅道单与本地缺陷保持关联且互不顶替；role 记录在关联上，同一证据对不同缺陷可不同。
